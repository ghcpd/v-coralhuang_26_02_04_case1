## Why this approach

- Tokenizer maps the literal word `tuple` to the token `TokenType.STRUCT` for ClickHouse. The parser uses the token text to decide function-specific parsing. That left `tuple(...)` using the generic function parser (which didn’t allow aliased arguments) rather than the struct parser that does allow aliased elements.
- I added a mapping for the ClickHouse dialect so that `TUPLE` (the token text) calls `_parse_struct()`. This lets tuple(...) parse with aliased args per existing struct semantics.
- Positional `.N` access after a dotted expression is a generic construct (not just ClickHouse), so I added a small generic branch in `_parse_column` that consumes `DOT NUMBER` and constructs a `StructExtract` expression. This generalizes to other struct-like functions and avoids dialect-specific hacks.

This design keeps parser behavior consistent: struct-like constructs with aliasable components continue to be parsed via the `_parse_struct` code path; numeric dotted access is handled consistently.

## Notes / Trade-offs

- I added the ClickHouse-specific mapping of the textual function name `TUPLE` -> `_parse_struct()`. This is minimal dialect-specific configuration and follows how other dialects register custom function parsers.
- The numeric dot-case handling is generic and minimal — it only triggers for a DOT followed by NUMBER; other dot usages (identifier access) are unchanged.
- The fix preserves round-trip parse → sql(dialect="clickhouse") → parse for the covered cases.
